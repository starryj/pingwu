# M11 · 认物与通用文案

> 0.11.0-m11 → 0.11.2-m11 / versionCode 17 → 19

## 一、这次改什么（作者的两条反馈）

1. 「香水这个，一旦我把香水换个方向，验证就识别不出来了」——原来本机判定只有一条路：YOLOX 数药片。非药品物品根本没有「认出它」的能力，换不换方向都认不出；只是药品恰好能靠数个数过关。
2. 「识别界面的提示语还是药品有多少颗之类的」——文案里写死了「颗 / 应服 / 到吃药时间了」，钥匙、证件、香水也被套上药品说法。

## 二、做法

### 1. 单位跟着分类走

`data/mock/MockData.kt` 的 `ItemCategory` 增加 `unit` 字段：

| 分类 | 单位 |
| --- | --- |
| 药品 MEDICINE | 颗 |
| 钥匙 KEYS | 件 |
| 证件 DOCUMENT | 件 |
| 其他 OTHER | 件 |

`unitOf(raw)` 供界面与判定共用；`LocalVerdictJudge.judge(..., unit)` 的失败文案改成「本机看到 3件，和应拍的 2件对不上。」

### 2. 非药品物品：用登记照「认物」

新增 `cv/ItemMatcher.kt`，用 OpenCV 的 ORB 特征做「同一件东西」比对：

- 两张图缩到长边 900，转灰度；
- ORB 提 1500 个特征点，Hamming 距离 + Lowe 0.75 比例检验得到 good matches；
- good ≥ 8 时做 RANSAC 单应矩阵，数内点 inliers；
- 判定：`(good >= 10 && inliers >= 5) || good >= 16`；
- 颜色直方图相关性只作为失败时的提示，不参与通过判定；
- 全部 `Mat` 在 `finally` 里 release。

ORB 本身是旋转不变的，所以「把香水转个方向」仍能对上；光照小变化也能容忍。失败时给三种人话：细节太少 / 颜色像但形状没对上 / 画面里没认出这件东西。

### 3. 拍照判定分两路

`CapturePlaceholderScreen.kt` 新增本地挂起函数 `localJudge(task, bitmap, filePath, report)`：

- **药品**：仍走 YOLOX 数颗数（数量 + 照片质量），文案用「应拍」；
- **非药品且有登记照**：`ItemMatcher.compare(cover, photo)`，通过条件是「认出来了 + 照片质量 OK」；失败时若质量问题优先说照片问题，否则说认物原因；
- **非药品但没有登记照**：退回数量判定（提示先去「物品」里拍一张样子）。

调试入口「用示例照片走一遍」对非药品 item 会把登记照旋转 90° 当成本次拍摄，用来验证「换个方向也能认」。

### 4. 文案去药品化

- 拍照页标题：药品「把X ×N 拍进框里」；其它「把「X」拍进框里」；
- 副标题：其它且已登记 →「摆好、看清楚，换个方向也认得出」；
- 取景框上方 chip：认物通过显示「认出来了 · N 个特征点对上」，失败显示「还没认出它」；
- 照片质量提示从枚举名改成中文（画面太小 / 太暗 / 太亮 / 几乎没有明暗变化）；
- 凭据页「判定」行不再写「N 颗」，改为「在线判定 / 本机判定」（数量在「数量」行已单独显示）。

## 四、已知边界

- 认物只回答「这是不是同一件东西」，不回答「事情做没做」——这一点和原来一样，凭据页仍写着「拍照只是在场证明」。
- 透明、纯色、几乎没有纹理的东西（玻璃杯、白纸）ORB 特征少，容易认不出；这类物品可以先用在线大模型 API 识别（我的 → 在线识别），或把封面拍得更有细节。
- 两件长得几乎一样的物品（同款两把钥匙）ORB 分不清，需要靠分类/数量/备注区分；后续可考虑加「只数件数」的通用模式。
- 旧版「模板匹配」代码（TemplateMatcher / RegistrationCheck）未接入拍照流程，仍是药品时代遗留，后续清理。

## 六、0.11.1 / 0.11.2：震动与提醒声音

作者 19:00 复测反馈：「能通过。不过现在有铃声，没有震动。在我的界面要有能设置铃声和震动的地方，铃声可以让用户自己选或者上传铃声。」

### 1. 为什么有铃声没振动

`adb shell dumpsys vibrator_manager` 里 pingwu 的振动记录全是：

```
effect | ignored_background | usage: UNKNOWN | com.pingwu.app
effect | ignored_for_settings | usage: UNKNOWN | com.pingwu.app
```

系统把「后台 App 发起的、没声明用途的振动」直接忽略了（Android 15+ 的限制）。屏幕亮、铃声在响，看起来像闹钟正常，但振动根本没执行。

修法：`AlarmPlayer` 振动时显式声明用途——

```kotlin
val effect = VibrationEffect.createWaveform(VIBRATION, 0)
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
    val attrs = VibrationAttributes.createForUsage(VibrationAttributes.USAGE_ALARM)
    vibrator.vibrate(effect, attrs)
} else {
    vibrator.vibrate(effect)
}
```

修后 真机 上的记录变成：`usage: ALARM ... played: [0,600,300,600,300,900]`，`CurrentVibration` 的 `mUsage=ALARM`、`status=running`。

### 2. 声音与振动统一由 AlarmPlayer 播

通知渠道 `pw_reminder_v3`：高优先级、`setSound(null, null)`、`enableVibration(false)`。通知只负责把人叫到全屏页；声音与振动由 `AlarmPlayer`（USAGE_ALARM）播放，这样全屏页没起来、渠道声音被系统吞掉，也不会「只亮屏没声没振动」。旧渠道 `pw_reminder_v2` 保留，避免已存在的通知失效。

### 3. 我的 → 提醒声音

- **选系统铃声**：`RingtoneManager.ACTION_RINGTONE_PICKER`（闹钟类型），选完保存 URI + 名称
- **从文件选**：`ActivityResultContracts.OpenDocument("audio/*")`，把音频复制进 `files/sounds/custom_ringtone.<ext>`，卸载前一直在
- **试听 3 秒**：直接调 `AlarmPlayer.start()`，3 秒后停
- **移除自定义**：删掉拷贝的文件，回到系统铃声
- **震动开关**：关掉后 `AlarmPlayer` 记录 `vibrate skipped: disabled in settings`
- 规则：换系统铃声会清掉自定义铃声（否则自定义优先，用户会觉得「选了没变化」）；选「无」= `silent=true`，到点只震动不响铃
- 偏好：`SharedPreferences(pingwu_reminder_sound)`，字段 `ringtone_uri / ringtone_label / custom_path / custom_label / vibrate / silent`

## 七、0.11.3 → 0.11.4：退出界面时的「画面重贴」

作者 19:26 反馈（附截图）：「在退出界面的时候会出现截图这种情况，画面重贴卡顿。」截图里物品页与物品详情页同时可见，内容重影。

### 1. 复现方式

`adb shell screenrecord --time-limit 14 --size 720x1600` 录屏 → `am start` → 点「物品」tab（1440×3200 屏上 `input tap 540 3060`）→ 点第一件物品（`input tap 720 780`）→ `input keyevent 4` 返回 → `ffmpeg -vf fps=30` 抽帧 → PIL 逐帧 diff 找变化段。另把系统动画放慢到 5 倍（`settings put global animator_duration_scale 5`，Compose 的 tween 也跟着变慢）录一遍，能拿到过渡的每一帧。

### 2. 根因

不是掉帧，也不是图片解码（`PhotoImage` 早就是 `LaunchedEffect` + `withContext(Dispatchers.IO)` + `LruCache`）：

1. 底色只画在 `PingWuRoot` 最外层 `Box` 的渐变上，**每个页面自己的背景是透明的**。NavHost 换页那一瞬两个 destination 同时存在（哪怕一帧），两个透明页面就互相透出来 —— 于是看起来像「两屏重贴」。
2. 底栏原来按 `route` 立刻判断显隐，切页时先被摘掉，正在滑出的那一页立刻重排一次，底部再闪一下「上一页内容」。

### 3. 改法（0.11.4）

- `ui/PingWuRoot.kt` 新增 `PwPage { ... }`：用 `LocalPwPalette` 的 `bg / bgGlow` 画和外层一样的垂直渐变，把 NavHost 里每个 destination 都包一层 —— **每页自己是不透明的**，叠着也不会透。
- 推进页（物品详情 / 添加 / 拍照）配左右滑动：`PUSH_MS = 220`，`slideInHorizontally(tween(220, FastOutSlowInEasing)) { it }` 推进来，退出去往 `-it/4`；退回时详情页往右滑走、被盖住的那页从左边滑回来。tab 之间仍是直接切（`None`），不做淡入淡出。
- 底栏不再中途消失：`ITEM_DETAIL` 也算「有底栏」的页面，从物品列表点进详情时底栏全程都在（推进完后也不摘），列表不会被抽掉底栏重排；只有进拍照 / 添加这类全屏页才在动画结束后收起。
- `AndroidManifest.xml` 的 `<application>` 加 `android:enableOnBackInvokedCallback="false"`，避免系统预测性返回再叠一层 App 内动画。
- 顺带修了一个同类小问题：滚动页（添加物品 / 我的 / 凭物）往下滑时，内容会穿到状态栏底下和系统时间叠在一起。`PwPage` 顶部铺一条和底色同色的遮罩（高度 = 状态栏 + 10dp，末段渐隐），拍照页除外（全屏相机）。

## 八、0.11.5 / 0.11.6：到点不再提前一分钟 + 认物改成「只认一件」

2026-11-13 晚上作者反馈两条：

### 1. 提前一分钟：查询里藏了 60 秒提前量

- 真因：`PingWuRepository.duePendingList()` 的过滤条件写成 `scheduledAt <= now + 60_000L`，而界面每 15 秒轮询一次，于是最坏提前一分钟弹出到点页。

| 时间点 | 画面 |
| --- | --- |
| T-69s 到 T-2s | 首页不变，没有到点页 |
| T+2s | 仍不变 |
| T+7s | 到点页出现（15 秒轮询的正常延迟，不再有任何提前） |

### 2. 认物：纯调阈值救不了，改成「默认只认一件」

真机取证（5 件物品 × 7 张证据照）用同一套 ORB 参数离线复算：

| 对照 | good / inliers | 结论 |
| --- | --- | --- |
| item-5 登记「Action+香水」 vs 实拍「勺子」 | 128 / 96 | 假样本分数最高 |
| item-2 同一个小盒换 45° | 91 / 79 | 真样本反而不如假样本 |
| item-3 单独 Action vs Action+盒子 | 42 / 11 | 真样本很低 |
| item-1 白纸上的一颗蒜 vs 同物远拍 | 2 | 纹理太少，ORB 直接失效 |

根因：登记照里有多件东西，画面里只要对上其中一件（Action 相机的特征极强）就判过；换东西也能过。

按作者选的 **C** 做两件事：

1. **本机只认一件**：登记引导改成「只把这一件东西放进框里，拍满一点」；判定只认这一件；登记照特征太少（关键点 < 10）时明确退回「只按数量算」，并在登记成功页提示「这张的细节有点少，想认得更准就靠近一点重拍」。
2. **在线比对登记照**：把现场照 + 登记照一起发给视觉模型，prompt 写明「第 1 张是刚拍的现场照，第 2 张是这件物品登记时的样子，先比较是不是同一件东西」；画面里只有别的东西要直说看到什么，不许替用户圆场。
3. 上传前把现场照压到长边 1280 / 质量 82，解码放到 `Dispatchers.Default`。

## 九、0.11.7：在线识别的开关离开页面就被关掉

作者反馈：在「我的」里填好 Key、测试连接成功后，切到凭物等其他页面，回来发现在线识别又被关了。

### 1. 真因：开关只是改草稿，没落盘

- 开关的 `onCheckedChange` 只更新了页面里的 `draft`，真正写盘只有「保存配置」按钮这一条路；「测试连接」也只验证、不保存。
- 于是「开了开关 / 测通了连接」都只活在当前这一页：`vm.aiConfig` 还是旧的（enabled=false），进程被系统回收后更是一干二净。
- 真机取证：`run-as com.pingwu.app cat shared_prefs/pingwu_ai.xml` 里 `api_key`、`base_url`、`model` 都在，唯独 `enabled=false` —— 说明配置存过，但开关那一下没存。

## 十三、0.13.0：一件物品可以有几个「样子」

### 1. 起因（作者实测反馈）

作者用 0.12.0 试了「一张照片登记几件」，提了三条：

1. 选了三件，App 把它们**各自建成了三条物品**（物件 1 / 物件 2 / 物件 3）。应该归到**同一件物品**里，不该拆成三条。
2. 这个功能不该单独放一个入口，应该并进「模板注册」里；时间也不该只能选「每天」，应沿用物品自己的提醒规则。

### 2. 改法：从「拆成多条物品」到「一件物品多个样子」

- 新增表 `pw_subject`：`id / itemId / name / coverPhotoKey / sortOrder / createdAt`，一件物品挂 N 块「认得的样子」（正面、反面、换个角度都行）。
- `pw_occurrence` 加 `doneSubjectIds`（逗号分隔）：记住这一次已经认到哪几块，下次只判剩下的。
- 数据库 `version 2 → 3`，写了 `MIGRATION_2_3`：建表 + 加列 + 把已有物品的那一张模板照迁成它的第一块（老数据不丢）。
- 入口搬家：「一张照片，登记几件」横幅从物品页删掉；物品详情里新增「认得的样子」卡（缩略图 + 「N 块」+ 按钮「拍下它的样子 / 重新拍，或再补一块」）。

- 点选页加了**双指缩放 + 双指拖动**：右下角 `− 100% ＋`，放大后点一下就（最多 6 块，带 ✕ 可删），主按钮「就认这 N 块」。

## 十六、0.16.0：两处「删记录」

作者要两件事（m11205）：

### 1. 记录是什么，删的是什么

一条「记录」= 一条待办（`pw_occurrence`）＋ 它名下的一行凭物（`pw_evidence`）＋ 本机照片文件。

```

### 4. 踩到的坑：记录删了，照片还在

```

## 十七、0.16.1 → 0.16.2：凭物数据里的「30 张照片 71.3MB」

### 1. 作者报的现象

0.16.0 装到手机上，他把记录全删了，但「我的 → 凭物数据」还写着「30 张照片 · 71.3MB」。

### 2. 查到的真相

- 数据库：`pw_occurrence 0 / pw_evidence 0 / pw_item 19` —— 记录真的删干净了。
- 磁盘：`files/evidence` 下**还有 30 个文件**。
- logcat（他一次删掉 32 条时）：

```
deleteFiles key=/data/user/0/com.pingwu.app/files/evidence/2026-11-13/dose-106-210126.jpg existed=false deleted=false
...
deleteRecords removed=32 files=0
```

每个 key 都是 `existed=false`：**数据库指的这些文件早就不在了**，而磁盘上那 30 个文件
没有任何一条记录指着它们——是**孤儿**。

孤儿从哪来：老版本「清空全部凭物」「删掉物品」只删记录、不删文件；照片文件名里的
occurrence id 和现存记录对不上，就是那时候留下的。

为什么一直删不掉：`stats()` 数的是「目录里所有文件」，而 `deleteRecords` 只按
`pw_evidence.photoKey` 删——**孤儿不在任何 key 里，永远碰不到**。

### 3. 改法：一次孤儿对账

新增 `EvidenceCleaner.purgeOrphans(context, keepKeys)`：

- 遍历 `files/evidence` 下所有文件；
- 把 `keepKeys`（当前所有 `pw_evidence.photoKey`）解析成 canonical 路径集合；
- 不在集合里的删掉，删完顺手清空目录。

四个触发点：

| 触发点 | 位置 | 作用 |
| --- | --- | --- |
| 删完记录 | `PingWuViewModel.deleteRecords` | 顺手把以前漏下的孤儿一起收掉 |
| 打开「我的」读统计 | `PingWuViewModel.photoStats` | 让「N 张」始终等于真实占用 |
| 清理旧照片 | `PingWuViewModel.cleanupPhotos` | 一并收孤儿 |
| 清空全部凭物 | `PingWuViewModel.clearEvidence` | 记录全清后所有照片都是孤儿 |

### 4. 三条保护

1. **只扫 `files/evidence`**：登记照在 `files/items`、铃声在 `files/sounds`，都不碰
   （实测 真机 上 `files/items` 23 个文件原样保留）。
2. **keep 集合来自数据库**：有记录指着就绝不删。
3. **60 秒新鲜期**：`now - file.lastModified() < FRESH_GRACE_MS` 的文件跳过。
   拍下照片到写进数据库之间有间隔，对账不能把「正在落库的那一张」当孤儿。

### 5. 验证

| 场景 | 设备 | 结果 |
| --- | --- | --- |
| 记录删空后打开「我的」 | 模拟器 | `purgeOrphans keep=0 removed=26`，文件清零 |
| 同一操作 | 真机（真机） | `purgeOrphans keep=0 removed=30`；`files/evidence` 0 个、`files/items` 23 个未动 |
| 界面数字 | 真机 | 「凭物数据」变 **0 张 · 0 B** |
| 新鲜期守卫 | 真机 | 放一个旧文件 + 一个刚复制的文件：`keep=0 removed=1 fresh_skipped=1`，旧的删、刚放的留 |

### 6. 还剩什么

- 「凭物数据」读一次就顺手对账，属于隐式副作用；如果哪天想改成显式按钮，

## 十八、0.17.0：我的页小 lockup + 开屏跟主题走

作者给的四个待办里，这一节收掉两个：我的页底部加一枚小 lockup、开屏按用户当前主题出。

### 1. 我的页底部 lockup

- 资源：`app/src/main/res/drawable-nodpi/pw_lockup_paper.png`（760×384，取自
  `docs/brand/source/lockup-transparent-brown.png`）、`pw_lockup_dark.png`（同尺寸，
  用 alpha 通道把棕色整体换成暖白 `#F5F2E8`，给深墨主题用）。
- 位置：`ProfileScreen.kt` 页脚，原来那行「凭物 · 拍下来，才算真的做过」拆成
  一张 `Image(width = 148.dp, alpha = .92f)` + 一行小字「拍下来，才算真的做过」。
- 两套主题各自取图：`if (mode == ThemeMode.PAPER) R.drawable.pw_lockup_paper else R.drawable.pw_lockup_dark`。

### 2. 开屏跟主题走（走了两次弯路）

目标：纸白用户冷启动，第一帧就该是米色底 + 墨棕线稿猫，不能先闪一下深墨。

**弯路一：只在 `onCreate` 里 `setTheme()`。**
Android 12+ 的系统启动画面（图标 + 背景色）是 system_server 在进程起来之前画好的，
用的是 Manifest 里这个 Activity 的 theme。`setTheme()` 执行时启动窗口早就画完了——
真机上 120ms 截图仍是深墨底白猫。

**弯路二：`activity-alias` 双入口。**
写了 `.LauncherDark` / `.LauncherPaper` 两个 `<activity-alias>`（各带自己的 theme
和 MAIN/LAUNCHER），用 `PackageManager.setComponentEnabledSetting` 切换。
`resolve-activity` 确实切到了 `.LauncherPaper`，但启动画面**仍然按目标
`MainActivity` 的主题**画——alias 上的 theme 不参与启动窗口。

**最终做法：两个真入口 Activity。**

```kotlin
// EntryActivities.kt
class DarkEntryActivity : MainActivity()
class PaperEntryActivity : MainActivity()
```

`MainActivity` 改成 `open class`，`onCreate` 里 `setTheme(...)` + `LauncherAlias.sync(...)` 保留
（直接进 MainActivity 的路径——比如通知——也有正确主题）。

Manifest：`MainActivity` 去掉 MAIN/LAUNCHER；两个入口各带主题与 launcher filter，
`DarkEntryActivity` 默认 `enabled="true"`、`PaperEntryActivity` 默认 `enabled="false"`。

`ui/theme/LauncherAlias.kt`：

- `sync(context, mode)`：先 `setComponentEnabledSetting(目标, ENABLED, DONT_KILL_APP)`，
  再禁用另一个；
- 已处于期望状态就跳过，避免每次启动都写系统配置。

### 3. 验证

| 场景 | 期望 | 实测 |

| prefs `theme_mode=paper`，`resolve-activity` | `.PaperEntryActivity` | ✅ |

## 十九、0.17.1 → 0.17.2：开屏第一帧就是封面

### 1. 现象

作者：「开屏过程中会出现如截图这一个画面，这个画面可以不要，直接出现带文字的开屏图。」
截图是系统启动画面那一帧——米色底、正中一只墨棕线稿猫，没有文字。

### 2. 为什么会多出这一帧

Android 12+ 的启动画面由系统画，只有两样东西可配：一层**单色底** + 一枚**居中图标**
（`windowSplashScreenBackground` / `windowSplashScreenAnimatedIcon`）。0.17.0 把封面里的
那只猫当成了这枚图标，于是点图标先看到「猫 + 底色」，带文字的整张封面要等 App 第一帧之后才出来。
系统接口不支持整屏图，所以这一帧只能**要么有图标、要么只剩底色**。

### 3. 改法

- **图标置空**：新建 `app/src/main/res/drawable/pw_splash_blank.xml`（一个透明矩形），
  `values-v31/themes.xml` 里两套主题的 `windowSplashScreenAnimatedIcon` 都指向它——那一帧只剩底色。
- **封面用普通 View 画**：`MainActivity` 用 `FrameLayout` 装两层，上层是写死封面的 `ImageView`
  （`splash_paper` / `splash_dark`，`CENTER_CROP`，底色 `pw_paper` / `pw_ink`），第一帧只画它，
  系统启动画面立刻收走；第一帧画完（`addOnPreDrawListener`）再把 `ComposeView` 加进来压到封面底下
  （`addView(content, 0, ...)`），同时开始计 1000ms 停留，之后 320ms 淡出。
  这样封面从「点图标」那一刻就在，不会再等 Compose 组合。
- **通知 / 闹钟回 App 走 `OpenAppReceiver`**：通知是一段时间前建的，若它指向的入口后来被切主题禁用，
  点下去就没反应。改成点下去那一刻读当前主题，再启动对应入口（`LauncherAlias.entryClass()`）；
  `ReminderActivity` 的「去拍照」是前台启动，直接用 `entryClass()`。
- 顺带：`LauncherAlias.sync()`（读/写 PackageManager）挪到首帧之后再跑，不占启动时间。

### 4. 验证

| 场景 | 期望 | 实测 |
| --- | --- | --- |
| 纸白冷启动帧序列 | 桌面 →（纸色）→ 带文字封面 | ✅ 无猫图标帧（`docs/shots/m17-2-splash-paper.png`） |
| 深墨冷启动帧序列 | 桌面 →（近黑）→ 白线稿封面 | ✅（`docs/shots/m17-2-splash-dark.png`） |
| 系统启动画面那枚图标 | 不出现 | ✅ 两套主题均为透明 shape |
| 封面停留 | 1s + 320ms 淡出 | ✅ |
| 通知「去拍照」 | action 指向 broadcast | ✅ `dumpsys notification`：`[0] "去拍照" -> broadcastIntent` |
| 全屏页「去拍照」 | 进当前主题入口 | ✅ 深墨时 `topResumedActivity=.DarkEntryActivity` |
| 冷启动 `Displayed` | — | 540–600ms（debug 包） |
| 单测 / Lint | 29/29、0 error | ✅ |

版本 `versionCode 36` / `0.17.2-m17`。

### 5. 还剩什么

- 桌面打开动画本身约 0.3–0.45s，这段时间是纸色 / 近黑底（与封面同族，不是白屏闪烁）；

- `app/src/main/java/com/pingwu/app/ui/SplashCover.kt`（`PingWuSplash`）已无引用，文件先留着
  （删文件按规则要先问）。

## 二十、0.17.3：到点不弹全屏 + 点通知像「直接关掉」

### 1. 现象（2026-11-14 22:25，十一在真机上遇到）

- 22:25 阿米替林到点：响铃了，但只有通知栏横幅，**没有全屏到点页**。
- 点那条通知：App 像「被关掉」——什么都没发生；过一会儿手动打开 App，验证页才出来。

### 2. 根因

**① 全屏 Intent 被系统降级**

`ReminderNotifier.notify()` 把通知类别写成 `NotificationCompat.CATEGORY_REMINDER`。
Android 14 起，全屏 Intent 只对 `CATEGORY_CALL` 和 `CATEGORY_ALARM` 放行，其它类别系统会
静默降级成横幅——不报错、不打日志，所以之前一直「看着正常」。

改成 `CATEGORY_ALARM`（自检通知本来就是 ALARM，所以自检能弹、真的提醒弹不出来，正好对上）。

**② 点通知后导航崩溃**

crash buffer 里的原话：

```
java.lang.IllegalArgumentException: Cannot navigate to capture.
Navigation graph has not been set for NavController ...@7037000
    at com.pingwu.app.ui.PingWuRootKt$PingWuRoot$3$1.invokeSuspend(PingWuRoot.kt:161)
```

`LaunchedEffect(initialRoute)` 在 NavHost 还没装好图的时候就 `nav.navigate(Routes.CAPTURE)`：
冷启动时 compose 刚起来就跳，必然抛异常，进程被杀——所以「点了一下，什么都没了」。

### 3. 改法

- `app/src/main/java/com/pingwu/app/ui/PingWuRoot.kt`：等 `nav.currentDestination != null`
  （最多等 2 秒、每 50ms 看一眼）再跳，并且 `runCatching` 兜底，失败只记
  `Log.w("PwNav", ...)`，不让它再崩进程。
- `app/src/main/java/com/pingwu/app/reminder/ReminderNotifier.kt:138`：
  `setCategory(NotificationCompat.CATEGORY_ALARM)`。

### 4. 验证（真机 Android 16）

| 用例 | 做法 | 结果 |
| --- | --- | --- |
| 冷启动直落拍照 | `am start --es route capture` | `TotalTime 549`，`PwNav` 见 `route=capture`，crash 0 ✅ |
| 息屏弹全屏 | 测试入口「5 秒后发提醒（先锁屏）」+ `keyevent 223` | `mWakefulness=Awake`、`topResumedActivity=.reminder.ReminderActivity`、`PwAlarm start reason=activity` ✅ |
| 全屏页「去拍照」 | 点按钮 | 落在 `PaperEntryActivity`，crash 0 ✅ |
| 通知本身 | `dumpsys notification` | `fullscreenIntent=PendingIntent{...}` 已挂上 ✅ |
